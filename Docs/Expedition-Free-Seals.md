# Existing expedition: choose either purification seal

Only the existing five-room expedition Purify objective changes. A remains at `(-mirror*8,0,-6)` and B at `(mirror*8,0,9)`. Both are visible from room admission, with stable ground letters and independent three-second progress. The host queries actual enemy footprint overlap and LOS separately for each ring; pressure at B cannot pause capture at A. Leaving, contest and pause preserve each ring's progress. Completed rings keep their identity and point toward the nearest unfinished ring, or the exit after both finish. No additional input button is needed.

The room state exposes `SealProgress`, `SealComplete`, `AdvanceSeal` and `CaptureFraction`; the older `Advance` entry retains ordered compatibility, while the actual live host addresses both rings explicitly. `RoomSealView(index)` reuses the existing ChapterSealPresentation snapshot without changing chapter behavior. TacticalCaptureVisual has an explicit room-seal owner mode and keeps combat-epoch rejection. Failed-result evidence reports independent A/B seconds so a B-first attempt is not lost behind the compatibility Progress getter.

There are no new rooms, saves, reward changes, clocks or enemies. The six primary enemies, optional-event eight-enemy cap, support radius/LOS, exact objective positions, terrain, deterministic seed selection and session-local anti-repeat history remain. Hunt, Escape, rest and boss conditions remain. SaveBeforeLeaving still precedes room advancement and combat retirement.

Scoped managed verification executes the actual room host/state/navigation with explicit scene and persistence-service doubles, both orders across all six layouts, real LOS obstruction, independent contest, pause/background/leave/resume, terminal rejection, save failure boundary and successful transition. It also executes the actual visual component's room adapter, retained identities, directions and epoch cleanup. Compiled forced-order, wrong-room-adapter and collapsed-B-evidence controls must fail their specific runtime assertions. Existing seed/chain, LOS/support and failure-evidence tests remain in place. A save-service double proves the host responds correctly to failed persistence; it is not a real disk-failure or Unity-engine test.

Unity gameplay, controller pursuit, visual legibility, touch operation and device timing are still unverified here. Seed/path/count assertions are not claims of varied or enjoyable play. This branch does not include the independent HUD implementation until integration; that change consumes the snapshot and aggregate APIs above.
